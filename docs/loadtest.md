# 压测报告

M2 的验收标准：

1. 10 万条同类报错 + 30 分钟 CPU 满载，只产生 **1 个 Incident**；
2. 500 个 Agent 模拟负载下服务器**稳定**。

两项都在 2026-10-24 的一次 30 分钟连续压测中同时验证，**通过**。

## 环境

| 项 | 值 |
| --- | --- |
| 机器 | Intel i5-9600KF（6 核），16 GB 内存，WSL2（Linux 6.18） |
| 服务端 | 单进程 Node.js 22，`LOG_LEVEL=warn` |
| 数据库 | 同机 PostgreSQL 16 + TimescaleDB，默认配置（`shared_buffers=128MB`） |
| 负载 | 500 个模拟 Agent + 1 个真实 Agent + 压测脚本本身，全部在同一台机器上 |

服务端、数据库、模拟器和 CPU 压力进程共用 6 个核，结果偏保守。

## 负载模型

`loadtest/sim.ts` 模拟 500 台主机，每台走完整的注册和签名握手，然后按真实 Agent 的节奏上报：

| 消息 | 频率 | 内容 |
| --- | --- | --- |
| heartbeat | 15 秒 | 队列深度、运行时长 |
| metrics | 60 秒 | 40 个指标点（CPU、内存、负载、磁盘、网络），随机游走 |
| procs | 30 秒 | Top 进程 |
| log.summary | 每 10 秒 5% 的概率 | 随机异常日志样本 |

连接在 60 秒内逐步建立，断线按退避重连。同时模拟控制台用户每秒请求一次 `/hosts`、`/overview`、`/incidents`。

`loadtest/storm.ts` 对**真实 Agent** 制造故障：30 分钟内匀速往它跟踪的日志文件写 10 万条带 Java 堆栈的同类报错（每条的订单号、耗时、请求 ID 都不同），同时在每个核上运行 `nice 19` 的忙循环，把 CPU 打满。

## 结果

### 去重：1 个 Incident

| 检查项 | 结果 |
| --- | --- |
| 写入日志 | 100,000 条 |
| 服务器日志分组 | 1 组，`ERROR c.e.order.OrderService - Order <N> failed after <N>ms (req=<UUID>)`，计数 **100,000**（无丢失、无重复） |
| Alert | 日志报错、CPU 使用率过高，各 1 个，均为 firing |
| Incident | **1 个**，合并了这台主机上的全部 Alert |
| 通知 | 未配置渠道，0 条 |

Agent 端的 10 秒窗口把 10 万条压成约 180 条上报（每窗口一条样本加计数）。测试机 `/workspace` 磁盘本身使用率很高，触发了一个磁盘告警，它也被合并进同一个 Incident，符合按主机合并的规则。

### 服务器稳定性

| 指标 | 值 |
| --- | --- |
| 连接 | 500 / 500，全程 **0 次断线**、0 次连接失败 |
| 发送消息 | 115,477 条，约 36 KB/s（zstd 压缩后） |
| 可靠消息 ack 延迟 | p50 16 ms，p95 95 ms，p99 772 ms，最大 6.6 s |
| 控制台接口延迟 | p50 8 ms，p95 52 ms，p99 145 ms，最大 5.2 s；**0 个错误** |
| 服务端 + PostgreSQL CPU | 平均 23%，峰值 34%（单核百分比，与 `nice 19` 压力进程争抢） |
| 服务端进程内存 | 约 110 MB，全程平稳（另一次 12 分钟复测，按 PSS 统计） |
| 服务端错误日志 | 运行期间 0 条。停机时曾有 384 条“连接已关闭”，原因是关闭顺序不当，已修复并复测 |

**已知问题：偶发的秒级延迟尖峰。** 大部分时间 ack p95 在 20–80 ms，但 30 分钟里出现过几次持续 10–30 秒的全局变慢，期间 p95 升到 1–6 秒，所有连接同时受影响，之后自行恢复，没有断线和错误。已排除服务端内存增长、TimescaleDB 后台任务和检查点（检查点同步时间都低于 1 秒）。原因还在排查，推测与同机 CPU 被压满时 PostgreSQL 的调度有关。对于目标规模（几十台主机，负载约为本次的 1/10），影响有限。

> PostgreSQL 的内存这次没有准确测到：各进程的 RSS 直接累加，共享缓冲区被重复计算，总数从 0.4 GB 增长到 2 GB，但真实占用远小于此。`sim.ts` 现在改用 PSS 统计，并单独输出服务端进程的内存。

### Agent 资源占用

在 30 分钟故障风暴中（每秒约 55 条多行报错、CPU 被打满）：

| 指标 | 值 |
| --- | --- |
| 常驻内存 | 28 MB → 33 MB，峰值 34 MB |
| CPU | 平均 3.3%（单核），处理每秒 55 条多行日志的解析、脱敏、指纹和计数 |

没有日志风暴时 CPU 低于 1%。systemd 单元的 `CPUQuota=20%` 和 `MemoryMax=128M` 留有充足余量。

## 如何复现

需要已构建的服务端（`pnpm --filter @pulse/server build`）和 Agent（`make -C apps/agent build`），以及一个**可以被清空**的数据库：

```bash
cd apps/server
LOAD_DATABASE_URL=postgres://pulse:pulse@127.0.0.1/pulse_load ./loadtest/run.sh
```

| 环境变量 | 默认 | 说明 |
| --- | --- | --- |
| `AGENTS` | 500 | 模拟 Agent 数量 |
| `MINUTES` | 30 | 故障风暴时长 |
| `LINES` | 100000 | 写入的报错条数 |
| `OUT` | `/tmp/pulse-load` | 结果目录 |
| `PORT` | 18080 | 服务端端口 |

脚本会启动服务端和一个真实 Agent，等模拟 Agent 全部连上后开始风暴。结果目录里有：

- `sim.json`：延迟分位数、每 10 秒一次的采样；
- `storm.json`：Incident、日志分组和 Alert 的核对结果，`pass` 为 true 时脚本以 0 退出；
- `agent-usage.txt`：每 30 秒一行，依次是时间戳、Agent 常驻内存（KB）和累计 CPU 时钟数；
- `server.log`、`agent.log`。

先用 `AGENTS=20 MINUTES=2 LINES=3000` 冒烟，3 分钟左右跑完。
